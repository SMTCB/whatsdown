Implementation plan

How we'll work

We'll use a light version of Scrum that fits a one-person hobby project:

Sprint = 1 week

About 6–10 hours of work. If life gets in the way, the sprint stretches. Scope doesn't grow to fill the time.

Planning (15 min)

Pick cards from the board into the sprint column. Each card has acceptance criteria, so "done" is never vague.

Demo + review (20 min)

Run the sprint's demo script. Write 3–5 lines in docs/sprints/S#-review.md covering what worked, what surprised you, and what changes.

Backlog = the board

The board is the source of truth for scope. Story points (1, 2, 3, 5, 8) are a rough size, not a promise.

Spikes first

Risky unknowns, such as long-running agents on Vercel, get a timeboxed spike in Sprint 0 before anything is built on them.

Decisions logged

Any real choice becomes a short ADR (Architecture Decision Record) in docs/adr/, so you remember why later.

Change from the proposed approach

Claude and Groq are called through their own SDKs behind a small lib/llm router, instead of the Vercel AI SDK. Claude's prompt caching, effort and refusal-fallback settings are first-class in the native SDK, which keeps the agents cheaper and easier to tune.

Sprints

S0

Foundations & spikes

An empty but deployed app, and proof that the three risky pieces work.

Stories

  • WD-1 Scaffold the Next.js + TypeScript app locally (lint, Prettier, Vitest, .env.example).
  • WD-2 Create the Supabase project whatsdown. Link the CLI and add the first migration (projects, tickets, ticket_events).
  • WD-3 Spike: LangGraph.js with the Postgres checkpointer. Run a 3-node graph that pauses on interrupt() and resumes by thread_id.
  • WD-4 Spike: Inngest on Vercel. A step resumes the graph in a loop of about 240 s per call until the graph pauses or ends.
  • WD-5 Spike: E2B. Clone the fantasy repo read-only, run rg, and time an npm ci && npm run build.
  • WD-6 Register the GitHub App whatsdown-bot and install it on WCFantasyFootball only.
  • WD-7 Create the WhatsDown GitHub repo, push, connect it to Vercel, and set env vars. Add a CI workflow.
  • WD-8 Write ADR-001 (stack) and ADR-002 (durable execution pattern) from the spike results.

Demo

Open the Vercel URL and see a "Hello WhatsDown" page with a health check showing DB ✓, Inngest ✓, E2B ✓ and GitHub App ✓.

Exit criteria

  • All three spikes pass, or the ADR records a fallback (e.g. Inngest → Vercel Cron + queue table).
  • A push to main deploys automatically.
  • No secrets in git (.env.local is ignored).
S1

Web intake & admin console

Anyone can file a ticket. You can see it, with its full history.
  • WD-9 Public report form (title, what happened, steps, expected, screenshot, contact email), with spam protection (honeypot + rate limit).
  • WD-10 Admin login (Supabase magic link, allowlisted email) and RLS policies.
  • WD-11 Ticket list (filter by status and project) and ticket page with an event timeline.
  • WD-12 Project registry page: the fantasy app row (repo, commands, context files, Node version, denylist).
  • WD-13 Ticket event log helper. Every state change writes a ticket_events row.
  • WD-14 Playwright smoke test: submit the form, then see the ticket in admin.

Demo

File "Leaderboard shows wrong points" from your phone. It appears in the admin list as new.

Exit criteria

  • Anonymous users can't read tickets (RLS tested).
  • Screenshot upload is limited to 5 MB and image types only.
S2

Triage agent

New tickets are screened, classified and de-duplicated automatically.
  • WD-15 lib/llm router (Groq + Anthropic clients), logging every call to llm_usage.
  • WD-16 Injection screen with Prompt Guard. Flagged text is quarantined and an admin is notified.
  • WD-17 Triage node: type (bug, feature, question), severity, area, completeness score. Zod-validated JSON.
  • WD-18 Duplicate check with pg_trgm similarity against open tickets, and a link to the likely original.
  • WD-19 needs_info loop: triage asks up to 2 follow-up questions through a reply link on the ticket page.
  • WD-20 Triage eval set: 20 hand-written sample tickets with expected labels, run with npm run eval:triage.

Demo

File a vague ticket. Triage asks one question. Answer it, and the ticket moves to triaged with labels. File a near-duplicate, and it is linked.

Exit criteria

  • At least 85% label accuracy on the eval set.
  • Stays inside Groq free limits (calls are counted in llm_usage).
S3

Diagnostics agent & Gate 1

The agent reads the real code, explains the likely cause, and waits for your OK.
  • WD-21 Sandbox tools (read-only mode): search_code (ripgrep), read_file, list_dir, git_log. Size-capped output.
  • WD-22 Context loader: CLAUDE.md + docs/DOCS_MAP.md from the target repo, prompt-cached.
  • WD-23 Diagnostics node (Claude with tool use, adaptive thinking, budget cap). Output: root cause, evidence (file:line), fix plan, risk, confidence.
  • WD-24 Gate 1 UI: Approve, Reject or "Revise with note" on the ticket page. The graph resumes from interrupt().
  • WD-25 Cost guard: stop the run and mark it failed if a ticket exceeds its $ budget (default $1.50).

Demo

A real (or replayed) fantasy bug gets a diagnosis report with file references. Click "Revise", add a note, and see a revised plan.

Exit criteria

  • Diagnosis never writes to the repo (read-only token + sandbox mode).
  • Every tool call is visible in LangSmith.
S4

Developer agent & pull request

An approved plan becomes a real pull request on the fantasy repo.
  • WD-26 Sandbox write mode: edit_file (str-replace), run_check (lint, build, madge, unit tests only).
  • WD-27 Developer node: apply the plan, run checks, self-fix up to 2 times.
  • WD-28 Diff guard. Block changes to supabase/migrations/**, supabase/functions/**, .github/**, package*.json, ios/**, android/**, middleware.js, vercel.json and capacitor.config.ts. Also cap the diff size.
  • WD-29 PR creator: the GitHub App pushes branch agent/<ticket-id> and opens a PR with the diagnosis, the diff summary and a "made by WhatsDown" label.
  • WD-30 BACKLOG.md entry added in the same PR (decided: yes). After the PR opens, the app adds a second commit that inserts ## 🟡 <title> (<date>) — PR #<n>, WhatsDown ticket #<t> plus 2–4 bullets (cause, change, files) just below the header. It doesn't touch the "Last Updated" line. If BACKLOG.md conflicts, the app rebuilds the entry on the latest main.

Demo

Approve a plan. Within minutes a PR appears on GitHub with a clean diff, and Vercel posts a preview link.

Exit criteria

  • A test patch that touches a migration is blocked (unit test).
  • The sandbox has no production secrets, and the app (not the sandbox) does the push.
S5

QA agent & Gate 2

CI results are read automatically. Your merge closes the loop.
  • WD-31 GitHub webhook endpoint (signature check) for check_suite, check_run and pull_request.closed.
  • WD-32 QA node: wait (interrupt) for CI, then summarise the pass/fail and post a PR comment.
  • WD-33 Failure loop: send the CI logs back to the Developer, up to 2 retries, then escalate (failed + your attention).
  • WD-34 Gate 2: merging the PR on GitHub resumes the graph (merged). Closing it without merging cancels the graph.
  • WD-35 Timeout handling: CI silent for 90 min → reminder; PR unmerged after 7 days → nudge.

Demo

The PR's CI goes green and a QA comment appears. You merge, the ticket shows merged, and Vercel deploys.

Preview caution

Vercel previews of the fantasy app may point at the live Supabase. Use them only to look around, never to test writes.

S6

Communicator, observability & evals

Reporters hear back. You can see cost, speed and quality.
  • WD-36 Communicator node: plain-language updates at triaged, awaiting_merge and merged, sent by email (Resend).
  • WD-37 Metrics page: tickets by status, time-to-PR, cost per ticket, Groq quota used.
  • WD-38 Replay benchmark: 10 historical bug-fix PRs from the fantasy repo. Check out the parent commit, run diagnosis and developer, and compare with the real fix.
  • WD-39 Model experiment: Opus 5.5 vs Sonnet 5.5 on the benchmark. Record the result in an ADR.
  • WD-40 Prompt catalogue: all prompts in prompts/*.md with version numbers.

Demo

An end-to-end ticket: form → email updates → merged fix. A benchmark score card shows e.g. "6/10 correct file, 4/10 equivalent fix".

S7

WhatsApp intake

Report a bug by WhatsApp, including photos and voice notes, and get updates there.
  • WD-41 Meta developer app + WhatsApp test number. Verify your phone as a recipient.
  • WD-42 Webhook: GET verify token, POST with X-Hub-Signature-256 check, idempotent by message id.
  • WD-43 Phone allowlist (reporters table). Unknown numbers get one polite reply and nothing else.
  • WD-44 Conversational intake: the Triage agent chats to fill missing fields, then confirms "Shall I open this ticket?"
  • WD-45 Media: images → Storage; voice → Whisper transcript attached to the ticket.
  • WD-46 Outbound updates: free-form inside the 24 h window; an approved ticket_update template outside it.

Demo

Send a voice note: "the transfer button does nothing". A ticket is opened, and you later get a WhatsApp message saying it's fixed.

Lead time

Template approval by Meta can take hours to days. Submit the template on day 1 of the sprint.

S8

Hardening & second project

Make it robust, then prove it's app-agnostic.
  • WD-47 Threat-model review and fixes (webhook replay, prompt injection via repo content, token scopes).
  • WD-48 Runbooks: stuck ticket, Groq quota hit, E2B down, revoke GitHub App.
  • WD-49 Onboard a second hobby app through the registry only (no code changes). That proves the platform is app-agnostic.
  • WD-50 Embedding-based duplicate check (pgvector) if trigram matching proves weak.
  • WD-51 Retrospective of the whole build: what to keep, cut or try next.

Local → GitHub → Vercel

1 · Build locally→ 2 · git init + first commit→ 3 · Create GitHub repo, push→ 4 · Import in Vercel→ 5 · Branch protection on main
  1. Days 1–3 of S0: work only on your machine. Supabase is already in the cloud, so local code talks to the real whatsdown project, which is fine because it holds no user data yet. Run Inngest's dev server locally with npx inngest-cli dev.
  2. End of S0: create a private repo whatsdown on GitHub, push, and import it in Vercel. Add all env vars in Vercel (Production + Preview). Connect Inngest via its Vercel integration.
  3. From S1 on: every story gets a branch → PR → CI → merge to main → automatic production deploy. Previews get their own URL.
  4. Migrations: written with the Supabase CLI (supabase migration new) and applied with supabase db push by you. Never applied by agents.

Definition of done

  • Acceptance criteria on the card are met and shown in the sprint demo.
  • Lint, typecheck, unit tests and build pass in CI.
  • New env vars are added to .env.example and the env table.
  • Any schema change is a migration file, and the data model doc is updated.
  • Agent prompts are versioned in prompts/, and a LangSmith trace was checked once.
  • The doc register entries touched by the story are updated.

Risks & mitigations

RiskImpactMitigation
Agent runs exceed Vercel's time limitHighInngest step loop with checkpoint resume (spike WD-4). Fallback: a queue table plus Vercel Cron.
Agent breaks the live fantasy appHighDiff guard, PR-only, your merge required, branch protection, no prod secrets in the sandbox, no e2e against prod.
Groq free quota runs outMedUsage tracking, a backoff queue, and automatic fallback of light tasks to claude-haiku-5-5.
Claude cost creepMedPer-ticket $ budget, prompt caching, effort tuning, and a monthly cap set in the Anthropic console.
Prompt injection via ticket text or repo filesMedPrompt Guard screen, tool allowlist, read-only diagnosis, a human gate before any write.
WhatsApp template rejected or delayedLowSubmit early. Email fallback stays on.
Scope creep (it's fun!)LowNew ideas go to the board's backlog, never into the running sprint.
