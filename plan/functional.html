What WhatsDown does

This spec describes the platform's behaviour in plain language: who uses it, what happens to a ticket, what each agent is allowed to do, and where you stay in control. It contains no implementation detail; that lives in the technical spec.

1. Scope and goals

WhatsDown receives problem reports about a registered app and runs them through a team of AI agents that end with a pull request you can merge. The first registered app is the Forza Fantasy League. The design doesn't depend on that app, so others can be added later.

Goal 1 · Learn

Understand how agentic workflows behave in practice: where they help, where they fail, what they cost.

Goal 2 · Shorten fixes

Go from a report to a reviewed PR without you reading the code first.

Goal 3 · Stay safe

Nothing reaches production without your two approvals. Agents never touch live data.

3. Ticket lifecycle

A ticket is always in exactly one status. Every change of status is written to the ticket's history with a timestamp and the cause.

Amber = waits for you. Blue = waits for the reporter. QA can send a ticket back to patching up to two times before it fails.

4. Intake channels

4.1 Web form (Sprint 1)

  • Fields: app (pre-selected), what happened, what you expected, steps, page or screen, optional screenshots (max 3, 5 MB each), contact preference.
  • You must be signed in (magic link) to submit.
  • Once you submit, you see the ticket number and a link to its page.

4.2 WhatsApp (Sprint 7)

  • Only numbers on the allowlist are answered. Other numbers are ignored and logged.
  • The conversation is guided. The bot asks for the missing pieces one at a time (what, where, when) and then confirms with a short summary before it creates the ticket.
  • Photos are attached to the ticket. Voice notes are transcribed and the transcript is shown on the ticket.
  • Reply STATUS to get the state of your latest ticket, or STOP to opt out.
  • Messages more than 24 hours after the reporter's last message use an approved template (WhatsApp rule).
Screening

Every report, on any channel, is first checked for prompt-injection attempts, such as text that tries to instruct the agents. Flagged reports go to needs_info with a note for you. The agents never see that text as instructions.

6. Approval gates

Gate 1 · Plan approval

Before any code is written

The ticket page shows the diagnosis: the cause in plain language, the evidence as links to file lines, the proposed change, the risk and the confidence. You choose one of:

  • Approve: the Developer agent starts.
  • Revise: you add a note and Diagnostics tries again (max 3 rounds).
  • Reject: the ticket is closed and the reporter is told.
Gate 2 · Merge

Before anything reaches users

You review the PR on GitHub, including the Vercel preview link. Merging is your action and only yours. WhatsDown detects the merge and continues. Closing the PR without merging moves the ticket to closed.

Database migrations are never part of an agent PR. If a fix needs one, the plan says so and you apply it yourself.

11. Out of scope (for now)

  • Agents applying database migrations or deploying edge functions.
  • Auto-merging, even for small fixes.
  • Feature requests beyond small changes; these are triaged and parked.
  • Multiple owners, teams or roles.
  • Channels other than web and WhatsApp (email intake, Slack, Discord).
  • Running end-to-end tests against production.

12. Acceptance of the whole system

  • A real bug reported on the web form ends as a merged PR with no code written by you.
  • A WhatsApp voice note produces a correct, complete ticket.
  • An injection attempt in a report is caught and does not affect agent behaviour.
  • A change to a protected path is blocked and explained.
  • The replay benchmark solves at least 4 of 10 historical bugs within budget.
  • Average cost per ticket is shown and stays under the budget.
