PROPOSED APPROACH · DRAFT 1 · FOR REVIEW

Maintenance agents, scoped for a hobby build

A ticketing app on Vercel and Supabase where a bug report goes through triage, diagnosis, a fix and a test run. You approve at two points. The first target is your fantasy sports league repo. The goal is to learn how well this works, so the plan builds in small stages and measures each one.

Summary

  • One TypeScript repo. Next.js on Vercel for the form, ticket pages and your approval screen. LangGraph.js for the agent workflow. Supabase for data and login.
  • You are the only approver. Approvals are buttons on the ticket page. The second gate is simply you merging the pull request on GitHub.
  • Ship in stages. Phases 0 to 2 give you a working ticket tool with triage and a written diagnosis. Code changes and test runs come after you have seen the diagnosis quality.
  • Free models first. Groq free tier as default, with one setting per agent so you can swap a single agent to a paid model when free quality becomes the bottleneck.
  • Measure from the start. A set of planted bugs in your repo tells you the success rate, cost and time per phase.

Ticket lifecycle

Each ticket is one LangGraph thread. The graph stops at three waiting points and resumes when the answer arrives.

flowchart TD
  A[Form submitted] --> B[Triage agent]
  B -->|duplicate| X[Link to existing ticket]
  B -->|missing info| C[Ask reporter for details]
  C --> B
  B -->|out of scope| Y[Close with reason]
  B -->|valid| D[Diagnosis agent]
  D --> E{You approve the plan?}
  E -->|reject with note| D
  E -->|approve| F[Developer agent]
  F --> G[QA step]
  G -->|fail, retries left| F
  G -->|fail, no retries| H[Escalate to you]
  G -->|pass| I{You review and merge PR}
  I -->|merged| J[Communicator agent]
  J --> K[Closed]

Ticket statuses

new · needs_info · duplicate · triaged · diagnosing · awaiting_plan_approval · patching · in_qa · awaiting_merge · merged · notified · closed · failed. Every change writes one row to an event log, which gives you the audit trail for free.

The two approval gates

  • Gate 1, plan approval. You read the diagnosis on the ticket page and choose approve, reject with a note, or close. A rejection sends your note back to the diagnosis agent.
  • Gate 2, merge. The agent opens a pull request with the QA result as a comment. You review and merge on GitHub. A GitHub webhook tells the app, and the ticket resumes. Until the webhook is built, a "mark merged" button does the same.

Models and cost

Expectation

Groq's free tier has tight per-minute token limits, and the open models on it are weaker at multi-file code edits than the best paid models. Triage and communication will work well. Diagnosis will work on small repos. Patching is where you will most likely hit the ceiling. That is a useful result of the experiment, not a failure.

  • Models are configured by role, not by name: triage, reasoning, coding, summary. Changing a model is a settings change.
  • Each run has a hard budget: maximum steps, maximum tokens and maximum minutes. When a budget is hit the ticket stops and asks you.
  • Rate-limit handling: queue and retry with backoff, and an optional fallback model per role.
  • Suggested paid fallback for later: a small prepaid balance used only for the coding role, so the cost stays a few dollars.
  • Every model call is logged with tokens and cost, even when the cost is zero.

Other running costs: Vercel Hobby, Supabase free, LangSmith free, Inngest free and E2B starter credits should cover a hobby workload. Free tiers change, so we verify limits when we build each phase. Supabase free projects pause after a period of inactivity, which is fine for this use but worth knowing.

Safety

Ticket text is untrusted input and the agents hold repo access. The design limits what a bad ticket can do.

  • Repo access. A GitHub fine-grained token limited to the chosen repos, with contents and pull request write only. Branch protection on main so nothing merges without you.
  • Tokens stay outside the sandbox. The sandbox gets a short-lived read token to clone. The app, not the model, pushes the branch.
  • Diff check in code. Changes to files outside the approved list, to dependencies, to CI files or to config fail the run automatically.
  • Public form. Bot protection (Cloudflare Turnstile) and rate limiting. Agents treat the report as data and never as instructions.
  • Sandbox. No production secrets, a time limit, and outbound network only for installing dependencies if needed.
  • QA integrity. The developer cannot delete or weaken existing tests. A diff that does is flagged.
  • Duplicates and retries. Webhooks and form submits carry an idempotency key, so a repeat does not start a second run.
  • WhatsApp. Evolution API drives an unofficial WhatsApp Web session and can get the number banned. The official Cloud API is the safe option. It has a free test number for a few recipients, which is enough to learn.

Keeping it project-agnostic

  • Nothing about fantasy sports lives in the platform. Everything project-specific sits in a projects row.
  • Optional file in each target repo, for example MAINTAINER.md, with conventions, where tests live and known pitfalls. Agents read it first.
  • The ticket form takes a project from a dropdown, so adding a second app means adding a row, not changing code.
  • Test commands run from the project row. Language-specific logic lives only in the sandbox step.

Measuring how well it works

Your goal is to see how well this works. We build a small test set early: about ten bugs planted in a copy of your fantasy repo, from easy (wrong constant) to hard (logic across two files). After each phase we run the set and record:

  • Did the diagnosis name the right file and cause?
  • Did the patch fix the bug without breaking other tests?
  • How many tokens, how much time and how many retries did it take?

The same set lets you compare Groq models, then a paid model, with real numbers.

Open questions for you

What is the fantasy app built with, and does it have automated tests or a GitHub Actions workflow?

This decides how reliable QA can be. If there are no tests, the developer agent writes the first reproduction test, which is harder.

Is the repo private, and is the app already deployed on Vercel?

Private repos need the token setup in phase 0. A Vercel deployment lets us later report "fixed and live", not just "merged".

Who submits tickets: your league members, or only you for now?

Members mean we need contact details (email) on the form and stricter spam protection. I assume email for updates.

Are you open to a small prepaid balance (a few dollars) on a paid model for the coding role if free models fall short?

Recommended, but only after phase 2 results. Default stays free-only.

Do you want me to send reporters the final message automatically, or always show you a draft first?

Draft first for the early phases, automatic later once you trust the wording.

Do you want to use Inngest for long jobs, or would you rather run a small always-on worker?

Inngest is simpler and free. I will confirm Vercel's current time limits before phase 2 and only add it if needed.

Do you have a name for the platform and a GitHub account or org where its own repo will live?

Is the phase order right, in particular stopping to review after phase 2 before any code-writing agent is built?

Recommended, since diagnosis quality drives everything after it.
